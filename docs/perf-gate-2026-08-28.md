# 8 × 1 MB 编辑器门槛:一次失败的判读与修复(2026-08-28)

`npm run perf:editor` 判定 FAIL。三条不达标里,**主因不是编辑器慢,是门槛量错了东西**。
这份文档记录判读过程、改了什么、以及为什么改判定标准不算放宽门槛 —— 也记下我在过程中
判错的两件事。

## 失败的那次运行

`perf/last-run.json`(2026-08-28T04:51:19Z,win32 10.0.26100,32 核,Electron 43.4.0):

```
PASS  mounted viewers with 8 tabs   1      (≤ 1)
FAIL  input → next frame P95        143.8ms (≤ 120ms)
PASS  input → next frame max        159.6ms (≤ 400ms)
PASS  tab switch P95                209.2ms (≤ 900ms)
PASS  renderer peak working set     516.2MiB (≤ 700MiB)
FAIL  renderer after close (10 s)   501.1MiB (≤ 450MiB)
FAIL  released after close          15.1MiB  (≥ 80MiB)
```

按键拆解:读 value p50 0 ms · 写 value p50 11.7 ms · React p50 79.5 ms,
`inputBlock` p50 91.7 ms,`inputFrame` p50 120.2 ms。

## 一、输入延迟:几乎全是量法问题

**这条门槛之所以失败,主因是驱动的打字方式不是打字。**

`perf/driver.js` 每次按键把整个 948 KB 缓冲区通过原生 `value` setter 写回 DOM。整串替换
会让 Blink 丢弃 textarea 的 inner editor 并重排全部 12,001 行。真实按键是浏览器对光标所在
那**一行**做增量编辑。报告里 `写 value p50 11.7 ms` 这一项本身就是证据:人打字时插入由
浏览器内部完成,缓冲区根本不经过 JS。

一次性探针(裸 textarea,无 React)把这件事钉死了 —— 数字是 p50/p95:

| 试验 | 同步块 | rAF | **上屏** | 强制布局 |
|---|---:|---:|---:|---:|
| A 整串重写 + 2×countLines + 强制布局 | 88.6/102.1 | 110.1/127.8 | **119.5/135** | 74.2 |
| B 整串重写 + 1×countLines + 强制布局 | 86.8/102.7 | 108.5/129.1 | **119.7/138.4** | 74.5 |
| C 整串重写 + 1×countLines,无强制布局 | 12.9/15.5 | 103.3/123.3 | **120.8/138.5** | 0 |
| D 整串重写,别的都不做 | 12.4/14.1 | 89.7/105.2 | **121.7/137.7** | 0 |
| E 真实按键 + 2×countLines + 强制布局 | 6.7/8.7 | 6.8/8.7 | **13.1/18.9** | 0 |
| F 真实按键 + 1×countLines,无强制布局 | 6.4/7.1 | 6.5/7.1 | **12.6/13.4** | 0 |
| G 真实按键,别的都不做 | 6.7/7.3 | 6.8/7.3 | **13.1/17.9** | 0 |

三件事:

1. **A→C:去掉强制布局把同步块从 88.6 ms 砍到 12.9 ms,上屏时间纹丝不动(119.5→120.8)。**
   布局在绘制前总要发生一次;强制读 `scrollTop` 只是把它挪进了 input handler。我原以为
   这是主因 —— **单次按键的场景下,这个假设是错的**。
2. **E/F/G 全部约 13 ms,彼此无差别。**真实按键路径下强制布局根本不要钱(增量编辑只弄脏
   一行),`countLines` 也在噪声里(扫描 p50 0–0.3 ms)。
3. **整串重写 ≈ 120 ms,真实按键 ≈ 13 ms,约 9 倍。**这就是全部差距所在。

### 改了什么

`perf/driver.js`:默认改用 `document.execCommand('insertText')` —— Blink 给真实按键用的
同一条编辑命令,只改光标所在那一行,触发真正的 `input` 事件。

`perf/driver.js`:新增 `inputPaint`(rAF 回调里再排一个任务 = 该帧提交后),门槛判它;
`inputFrame` 继续报出来。不加这条,"把布局移出按键路径"会显示成一次大胜 —— 看 C 行,
同步块砍掉 86%,而屏幕上一点没变。标签切换同样改上屏口径。

`apps/web`:`countLines` 每次渲染只跑一次(原来 FileViewer 和 CodeSurface 各扫一遍同一个
948 KB 串);`shown` 统一计数与渲染的字符串。

## 二、内存:门槛从来没量过基线

`sampler()` 在页面**已经加载完**才启动,第一个样本就已经包含整个空工作台的常驻。所以
`rendererAfterCloseMiB ≤ 450` 和 `releasedAfterCloseMiB ≥ 80` 判的都是「空工作台 + 负载」,
却按「负载」来写。加一次基线采样,把两条改成相对基线的增量,是让门槛去判它自己写的那个
东西。

### 一个必须记下来的判断错误

改动之前,我据 `docs/test-report-2026-08-24.md` 的「8 根工作区、无文件标签、空闲 10 s →
进程树工作集 725.9 MiB」推断:本次进程树峰值 788.8 MiB,所以 8 个标签只加了约 63 MiB,
于是「关闭后回落 ≥ 80 MiB」**在结构上不可能满足**,是一条只有先浪费掉才能通过的门槛。

**这个推断是错的。**基线采样一上线就否掉了它:

```
[perf] baseline renderer 95.7 MiB · JS 堆 2.4 MiB
```

空工作台的渲染进程是 **95.7 MiB**,不是我从树基线里折算出来的 470–490 MiB。725.9 MiB 是
用户真实环境(8 个工作区根、真实 OMP、真实会话)的进程树;性能门槛跑的是全新数据目录、
一个工作区根、更新器指向死代理、没有 agent 进程 —— 两者的基线根本不是一个量级。**拿另一
套配置的基线去论证这套配置的门槛不可满足,是我的错误。**

按实测基线重算失败那次运行:空工作台约 95.7 MiB,8 标签峰值 516.2 MiB,全部关闭 10 s 后
501.1 MiB —— **负载增量约 420 MiB,关闭后仍未归还约 405 MiB**。

所以 `released ≥ 80 MiB` 指向的是**真实存在的东西**。改成增量口径是把这件事**说得更准**,
不是推翻一条不可能的门槛。(那 ~405 MiB 里有相当一部分是采样时没有任何 GC 压力:加上强制
回收之后,同样的负载关闭后只剩 43.4 MiB。)

### 改动

1. 驱动之前先量一次空工作台(面板挂载完、静置 3 s、强制回收后),记为
   `rendererBaselineMiB`;
2. 判定改成增量:`loadDelta`(峰值 − 基线,标签花了多少)、`retainedDelta`(关闭后 −
   基线,还剩多少)。两条都是上限,方向也对了 —— 占得少、留得少才是好。旧的
   `releasedAfterCloseMiB` 继续记录,但不再作为判定;
3. 基线和关闭后各在页面里跑两遍 `window.gc()`(`--expose-gc`),再读
   `performance.memory.usedJSHeapSize`,得到 `jsHeapRetainedMiB` —— 唯一能区分"应用还
   握着"和"分配器还没还页"的数字。10 秒空转不是任何东西被释放的理由;
4. 这两件事**在页面里做,不走 CDP**。第一版用调试器,`Memory.forciblyPurgeJavaScriptMemory`
   之后 detach,紧接着的 `executeJavaScript` 再也没有返回,整次运行在 30 s 上限处死掉,
   什么都没量到。**能把被测对象弄死的工具不是测量工具。**顺带也保证按键附近没有任何附着
   的调试器 —— 延迟绝不能透过调试器去量;
5. 页面答不上来时 `jsHeapRetainedMiB` 为 null,该项**判失败而不是跳过**;
6. `perf/driver.js` 在每个阶段边界记一次 JS 堆(`heapMarks`),用来解释工作集峰值由什么
   构成。`performance.memory` 只是属性读取,不扰动测量。

## 三、应用侧的 JS 引用是干净的

`closeAll` 逐个 `clearDraft`,`pruneViewerStates` 按已提交的标签集合清扫,
`onOpenFileRequest` / `botcf:turn-complete` 的监听器都有 cleanup,模块级只有
`draftStore` 和 `viewerState` 两个 Map,都跟着标签生命周期走,`viewersAfterClose` 实测
为 0。`jsHeapRetained` 把这个静态结论坐实了。

## 四、两个判断错误的收口

记下来不够 —— 让它们不能再发生才算解决。

### #1 跨配置借基线

门槛每次运行都量自己的空工作台(`rendererBaselineMiB`),所有内存判定都是相对它的增量 ——
这条路本身已经堵死。残留的陷阱是 `perf/thresholds.json` 里那个 `baseline` 区块仍然摆着
另一套配置的绝对 MiB,而它正是当初误导我的东西。现在该区块加了 `configuration` 字段,
写明它**不是本门槛的起点**、只有回归的形状可比、绝对值不可比,并指向该用哪个数。

### #2 未经测量就断定原因

断定"每次按键强制同步布局"是 79.5 ms 的主因 —— 探针证明单次按键场景下它一分钱不值。

**更要紧的是**:我保留这个改动时给的理由 —— "按键快过帧时它有意义,能合并布局" ——
**同样是推理,不是测量**。那是完全一样的错误,只是换了个方向。

所以 `perf/driver.js` 加了 `burst` 阶段:一帧内连打 N 键,**并且同一段连打再做一次、每键
后强制一次布局**。两种变体交替进行,机器漂移平摊到两边。A/B 不需要重新构建旧代码 ——
驱动在编辑之后、同一个栈上强制一次布局读,正是应用当初强制的那次。

**判决:理由不成立。**

```
连打 6 键 → 上屏   56.2 ms · 每键 9.4 ms
  同样但每键强制布局  54.8 ms · 每键 9.1 ms
```

强制布局那一组还快了 1.4 ms,在噪声内。原因很清楚:`insertText` 只弄脏一行,那次布局本来
就不要钱,合并 6 次免费的操作还是免费。**这个改动的理由撤销**(代码随后被 CM6 重写取代;
CM6 里 `value` 的比较是另一回事 —— 它防的是把文档替换成它自己,属于正确性)。

`burst` 阶段作为常设判定线留下:这个问题以后还会被问,答案应该是量出来的。

## 五、401 MiB 是 Blink 的,不是 JS 的

阶段边界的 JS 堆(已用/已提交 MiB):

```
开标签前 2.6/5.2 → 开完 13.3/17.5 → 打完字 40.9/44.6 → 切完标签 12.9/17 → 全关后 12.9/17
```

**JS 堆全程没超过 44.6 MiB 已提交,而渲染进程比空工作台高 401.5 MiB。**

所以约 360 MiB 是 **Blink 侧**的:一个挂载的查看器要为 12,001 行 textarea 加 12,001 行
行号 `<pre>` —— 约 24,000 行 —— 保留布局对象、行盒、字形与整形缓存、绘制记录。折合每行
约 15 KB。

**结论:内存的解法是虚拟化,不是分配纪律。**削减 JS 分配对 360 MiB 的 Blink 结构无效;
唯一能把它降下来的是让挂载的行数跟视口走而不是跟文件走。而延迟当时已经不需要虚拟化了
(20.1 ms 上屏),所以虚拟化是一个纯粹的内存决策。

## 六、虚拟化:CodeMirror 6

分两步做,顺序是有意的。

### 第一步:行号槽窗口化 —— 拿回 11%,但给出了关键的数

那 24,000 行里有一半是行号槽,纯装饰,完全自己渲染,不需要任何依赖。先把它改成只渲染
视口附近的窗口(视口 + 每侧 150 行)。

| | 窗口化前 | 窗口化后 |
|---|---:|---:|
| loadDelta | 401.5 MiB | 423.8 MiB |
| JS 堆已提交峰值 | 44.6 MiB | 107.7 MiB |
| **Blink 侧(差值)** | **≈357 MiB** | **≈316 MiB** |

loadDelta 看着涨了,是因为连打阶段多打约 72 键 × 948 KB ≈ 68 MB 临时缓冲区(JS 堆
44.6→107.7 正好对上)。扣掉它,Blink 侧从约 357 降到约 316,**约 11%**。

**砍掉一半的行只拿回 11%** —— 布局成本跟**字符**走不跟行走:行号是 5 字符,正文是
78 字符。这一条把剩余的约 316 MiB 定位在文本面上,也就把换掉 textarea 的收益规模量了
出来 —— 从"猜"变成"数"。

### 第二步:文本面换 CodeMirror 6

`CodeSurface` 整体重写。textarea 按定义持有整个缓冲区,Blink 为它的每一行建行盒,从外面
没法窗口化 —— 组件本身必须换。CM6 只渲染视口,`lineNumbers()` 原生窗口化(手写的
`ChangeGutter` 随之删除),改动区域改用 `Decoration.line` + 自定义 gutter marker,
`revealLine` / `currentLine` / `focus` 契约不变。

| | textarea | CodeMirror 6 |
|---|---:|---:|
| input → 上屏 P95 | 25.6 ms | **12.3 ms** |
| 按键同步块 p50 | 9.5 ms | **0.5 ms** |
| 连打 6 键 → 上屏 | 56.2 ms | **6 ms** |
| 打开每个标签 p50 | 284.8 ms | **20.8 ms** |
| 切标签 P95 | 195.9 ms | **36.4 ms** |
| renderer 峰值 | 518.9 MiB | **205.1 MiB** |
| **loadDelta** | **423.8 MiB** | **108.1 MiB** |

代价:bundle 从 332 KB 涨到 595.7 KB(gzip 104.5 → 190.5 KB)。`@codemirror/commands`
是必需依赖 —— textarea 有浏览器原生撤销,CM6 的 `history()` 在那个包里,不装就是功能倒退。

`perf/driver.js` 跟着改:CM6 的编辑面是 contenteditable 不是 textarea,选择器改按
`aria-label` 找,`.value` 全部去掉。`--legacy-typing` 删除 —— 它靠
`HTMLTextAreaElement.prototype.value` 整串重写,现在没有 textarea 可写,复现不了。
"30 个字符进了缓冲区"的整体断言也去掉了:视口渲染之后 DOM 里根本没有完整文档可数。替代
的是**更严的** —— 每次采样都断言 `insertText` 被接受**且**真的跟了一个 `input` 事件。

## 七、关闭后残留:判因,不判果

CM6 之后唯一不达标的一条:

```
FAIL  retained after close          83.5MiB  (≤ 80MiB)
PASS  JS heap retained after close  3.8MiB   (≤ 12MiB)
```

JS 堆强制回收后只剩 3.8 MiB,所以**不是应用还握着东西**。看阶段堆:

```
开标签前 3.4/6.2 → 开完 24.4/33.4 → 打完字 33/52.2 → 切完标签 50.4/73.7 → 全关后 50.4/73.7
```

**已提交**的 JS 堆从 6.2 涨到 73.7 MiB。回收之后已用只有 7.3 MiB —— 约 66 MiB 是
**已提交但空闲**的 V8 页,而工作集算的是已提交的页。

我先怀疑是自己把采样写坏了:`window.gc()` 和取样在同一个 tick,而 V8 是在一次 major GC
**结束之后**才把页还给系统。加了三秒等待(`BUDGET.releaseSettle`)之后 —— **只动了
4 MiB**(87.5 → 83.5),在运行间噪声里。所以等待不是原因,**V8 就是不还这些页**。

那 74 MiB 从哪来?每次按键、每次切标签,都把整份文档序列化成一个新的约 948 KB 字符串放进
React state。

`retainedDeltaMiB` 从 80 提到 110,**并且同时新增 `jsHeapCommittedPeakMiB ≤ 100`**。
工作集口径的残留隔着一层 V8 的页归还策略,量的是果;已提交堆峰值量的是因 —— 应用到底
申请了多少。后者才是会随代码变化而变化、值得拦住的那个数。`jsHeapRetainedMiB`(强制回收
后的真实残留)保持在 12 不动,泄漏检测的那条一点没松。依据写在 `perf/thresholds.json`。

## 八、门槛通过之后又做的三件

### 1. 拆掉「每次按键序列化整份文档」

`jsHeapCommittedPeak` 的唯一来源。CM6 自己持有文档,所以这条不必存在。

改成:编辑器每次变更只上报**便宜的事实**(`{ lines, length }`),文本通过
`CodeSurfaceHandle.getText()` 按需取。取的时机只剩三处 —— 保存、卸载前的 flush、有 diff
时的重锚定。

`dirty` 的判定随之改成先比长度、长度相同才比内容(`editor/draftPolicy.ts`)。日常打字每
一次插入删除都改变长度,所以永远走不到比内容那一步;而"撤销回原样"这类长度相同的情况
值得那一次比较 —— **一个撤销之后不肯消失的 ● 是在谎报未保存的工作**。

**丢编辑的那个坑,是这次改动里唯一需要小心的地方。**草稿缓存原来每次按键都写,现在只在
"第一次变脏"和"卸载时"写。而如果由 FileViewer 在自己的卸载清理里调 `getText()`,**React
会先跑子组件的清理** —— 编辑器已经销毁,`getText()` 返回空串,静默缓存一个空草稿,用户的
修改就没了。所以 flush 是**从编辑器推出来**的(`CodeSurface` 的 `onFlush`,在
`view.destroy()` 之前调用),而不是从 FileViewer 拉。

### 2. 纯逻辑抽出来做了单测

`editor/draftPolicy.ts` + `test/draftPolicy.test.ts`:脏判定的长度短路、撤销回原样判干净、
草稿缓存写一次不重写。

**没有引入 jsdom。**CodeMirror 在 jsdom 里每个元素都量成 0 像素,视口计算全是退化值 ——
那种"组件测试"测的是 stub 不是组件。真正覆盖 CM6 集成的是性能门槛(它开真窗口、真打字、
真切标签)。所以把值得钉死的判定抽成纯函数测掉,其余交给门槛,而不是装一个会产出假绿的
测试环境。

### 3. 编辑器从主 bundle 拆出

`EditorTabs` 改成 `lazy(() => import('./FileViewer'))`。对 Docker 部署(bundle 过网络)
是实打实的省;对桌面端(本地磁盘)更多是把成本挪到首次打开文件。**门槛会说话**:
`open per tab` 覆盖首次打开、含 chunk 拉取。那个数字如果变差,这条就该撤回。

## 九、拆完序列化之后:两件我又说错的

### #3 「74 MiB 的已提交堆是每次按键序列化整份文档造成的」—— 只对了一半

拆掉之后的实测:

| | 拆除前 | 拆除后 |
|---|---:|---:|
| `jsHeapCommittedPeak` | 87.6 MiB | **88 MiB** |
| heapMarks「打完字」已提交 | 71.2 MiB | **28.8 MiB** |
| heapMarks「切完标签」已提交 | 87.6 MiB | **88 MiB** |

**打字阶段的堆降了 42 MiB,峰值一点没动。**因为峰值根本不在打字阶段 —— 它在**切标签**:
24 次 `api.fileContent()`,每次一个 948 KB 的 JSON 响应、一次 `JSON.parse`、一份 content
字符串。那条路我没碰。

这是**同一个错误的第三次**:我把一个数归给了一个原因,而没有先把它拆开看。`heapMarks`
本来就摆在那里,阶段是分开的,我却只读了「打完字」那一格。

改动本身是对的 —— 每次按键不再产生一个 948 KB 字符串,长时间编辑一份大文件时这是持续
收益,而且 `dirty` 的长度短路和 `getText()` 按需取都是更干净的形状。**但它没有降低门槛
测的那个峰值,不该被记成"解决了 88 MiB"。**

切标签那 88 MiB 要不要继续追?我的判断是**不要**:它是"读一个 1 MB 文件"的固有成本乘以
24 次,`retainedDelta` 只有 36.3 MiB、强制回收后 JS 只留 5.5 MiB,没有泄漏,V8 撑大的堆
会被后续工作复用。继续压它要动 API 契约(让服务端返回 raw text 而不是 JSON 包裹),
收益不抵改动面。

### #4 lazy 加载让首次打开变慢了,而我立过"变差就撤回"

| | 拆分前 | 拆分后 |
|---|---:|---:|
| open per tab p50 | 20.8 ms | 23.9 ms |
| **open per tab p95** | **39.2 ms** | **57.3 ms** |

bundle:单块 595.7 KB → 主块 317.9 KB(gzip 100.4)+ 编辑器块 280 KB(gzip 91.1)。

**我立的判据是"`open per tab` 变差就撤回",它变差了 18 ms。**

但我现在认为**判据本身立得不好**:8 个标签只有第一次付 chunk 拉取,p95 在 8 个样本里恰好

所以这是一个取舍,不是单纯退步:桌面端一次性多 18 ms,Docker 部署首屏少 91 KB gzip。
57.3 ms 也仍在 150 ms 门槛内。

**已定:保留拆分,改判据。**`open per tab` 拆成两条 —— `openFirst`(第一个标签,含 chunk

## 十、把「还没做的」三件做掉

### 1. `InlineDiffView` 的窗口化,现在有门槛验证了

缺的从来不是判据,是**到达那个视图的路**。`内联` 只对 AI 改过的文件存在,差异只有一条路
能进到编辑器 —— OMP 报告工具调用 → `routes/chat.ts` 汇总成本轮 `files_changed` →
`useChatSession` 合并进 `changedFiles` → `FileViewer` 从那里读 `diff` —— 而门槛运行时 OMP
被指向死代理,正是为了不在测量中途装一个 agent 二进制。

所以**伪造上游,别的都不碰**。`harness/inject.js` 在一次发送期间替换 `fetch`,且只替换
`/api/chat/stream`,回答一段真的 SSE 字节流;消息是打进真实输入框、用真实回车发出去的。
从那段字节往后全是应用自己:`streamChat` 的解析、`changedFiles` 的合并、差异解析、按内容
重新锚定、行的构建、视图的渲染。这和门槛早就在做的两件事是同一类 —— 模型端点和更新服务器
也都是「不存在的上游,在它本该回答的地方被回答掉」。`apps/web` 里没有任何东西知道这个文件
存在,这是有意的:一个为测试开的口子会在重构之后继续绿着,而这个会响亮地坏掉。

夹具是每个文件 350 处改动(`perf/fixture.cjs`)。这个数按「必须能让它变贵」挑:折叠的
内联视图为每处改动展开一个上下文窗口,加上每条被删的行和每段被省略的区间各一行,约合
3,150 行 —— 全渲染就是约 12,000 个元素,而视口加 overscan 只放得下约 160 行。它同时被
应用**从上面**卡住:每个文件的差异必须小于 `DIFF_CAP`,否则 `changedFiles` 只留尾巴,而
被截断的夹具不是门槛以为自己写下的那个;`buildSessionDiff` 为此报错而不是交付。

判的是一对**结构不变量**,不是耗时:`inlineRowsMountedMax`(DOM 里最多多少行)配
`inlineRowsTotalMin`(视图建模了多少行)。后者是这里唯一一条下限,它存在的意义就是让前者
没法在一个「恰好没产生几行」的夹具上空手通过 —— 和 `maxMountedViewers: 1` 是同一种形状:
和机器无关,只在架构被改回去时失败。另外报出并判定切到内联的上屏时间、在其中跳着滚动的
上屏分位数,以及**单独记账的** `inlineDeltaMiB`。

内存分开记账是有意的。采样器现在留下整条时间线,驱动的阶段时间戳把它切成两段:
`loadDelta` 仍然只回答「八个大脏标签要多少」,`inlineDelta` 回答「三千行的差异视图要多少」。
合成一个峰值会让其中一个的回退藏在另一个后面。

生成器本身也被钉住了:`apps/web/test/sessionDiffFixture.test.ts` 用**应用自己的**
`parseEditRegions` / `applyAnchors` / `buildInlineRows` 解析它生成的差异,比对区域的种类、
起点、条数与总量。这不是形式主义 —— `anchorRegions` 会**丢掉**找不到的添加块,一份 `+` 行
与磁盘对不上的差异会被应用悄悄化为乌有,而在空视图上量出来的数字非常好看。

八·2 里拒绝 jsdom 的理由没有变:CodeMirror 在那里每个元素都量成 0 像素,视口计算全是
退化值,那种「组件测试」测的是 stub 而且会绿。缺的不是断言库,是**真实浏览器**。

而真实浏览器一直都在:性能门槛就开着一个。所以引导代码抽成了 `harness/app.cjs`(构建检查、
服务、会话、工作区根、窗口、阶段追踪、清理),`perf/editor-load.cjs` 和新的
`e2e/editor.cjs` 共用它 —— 同一份构建、同样跑在独立端口和独立数据目录上的服务、同一种
窗口、同一个页面。区别只在于拿它做什么:一个计时,一个断言。

`e2e/spec.js` 覆盖十项,都是这次替换带进来、之前没有任何测试的行为:变更经真实聊天流送达、
文件头的 `+N −M · K 处` 与「无法定位」、三种改动各自的行装饰**落在正确的行文本上**、滚出
视口装饰必须消失、滚回来必须回到同样的行、每处改动一根 gutter 条、点击条切到内联并把那一处

夹具是另一套(`e2e/fixture.cjs`),和性能夹具互相替代不了:`edited.ts` 小到一屏放得下全部
三处改动,每行写着自己的行号,于是「这个装饰在第 12 行」是**读出来**的;`oversized.txt`
故意超过 `MAX_FILE_CONTENT_BYTES`,因为那是抵达只读面的唯一办法 —— 而性能夹具刚好压在
那条线**以下**,理由正相反。

`npm run test:e2e`。任一项不通过退出码为 1;一项失败会**停下**(这些检查有顺序依赖),
剩余项标 SKIP,报告里看得见跑到哪一步。

### 3. 阈值:按四次运行重新推导

**这条原来的写法是「连跑三次之后应按��次结果重新推导,尤其是 `jsHeapCommittedPeakMiB`
(88 对 100 只有 12% 余量,GC 时机的噪声可能不止这个数)」。跑完之后:那句提醒是对的,
而且比它自己以为的更对。**

五次运行(2026-08-30,win32 / 32 核 / Electron 43.4.0;其中第一次早于十·4 的修复,但那处
修复不改变任何有分量的分配,它在每一条上都不是离群点)。按实测离散程度分三档:

| 档 | 指标与实测区间 |
|---|---|
| **精确**(离散 < 10%) | 内联建模行数 **3150(五次完全相同)**· DOM 内行数 **152(五次完全相同)**· input→上屏 P95 12.4–12.7 ms · JS 堆残留 7.0–7.1 MiB · 内联滚动 P95 10.7–12.5 ms · 切到内联 16.5–23.8 ms |
| **中等** | 首个标签 57.0–76.6 ms · 稳态 P95 33.3–42.0 ms · 切标签 P95 42.0–54.1 ms · loadDelta 83.1–112.8 MiB |
| **粗**(离散 31–140%) | renderer 峰值 206.1–280.8 MiB · inlineDelta 108.3–185.5 MiB · **jsHeapCommittedPeak 77.2–130.3 MiB** · **retainedDelta 41.8–100.5 MiB** |

最后一档四个数全都来自同一件事:**阶段结束时 V8 恰好向系统要了多少页**。同一个阶段
(「切完标签」)在两次运行里分别是 22.5/59.7 和 85.9/101.8 MiB(已用/已提交)。

所以 `jsHeapCommittedPeakMiB ≤ 100` 在**代码没有任何变化**的五次运行里失败了三次。
**那不是发现,那是一条坏掉的门槛。**它提到 160;`retainedDeltaMiB` 110 → 140;
`inlineDeltaMiB` 200 → 240;`rendererPeakMiB` 300 → 360。每一条都在实测最大值之上,
留出的余量按**实测到的**离散度给,而不是按猜的 —— 推导完之后又跑的一次把三个最大值都往上
推了一点(committed 124.3 → 130.3、loadDelta 106 → 112.8、切标签 53.5 → 54.1),而全部
仍在新线之内。这一次正好说明余量为什么要按离散度给:线若定在 130,它就会红。

**这不是让步,前提是把话说清楚:这四条现在是「防止大幅回退」的粗线,不是精细的。**
它们抓不住 20% 的回退 —— 实测离散度就是这么说的。而真正能发现泄漏的那条
`jsHeapRetainedMiB` 一动没动:四次都是 7.0–7.1 MiB,限 12,**四次之间没有任何漂移**。
`jsHeapCommittedPeak` 仍然值得留着(它判的是**因**),但它判得住的是「每次按键把整份文档
序列化进 React state」那种量级的回退 —— 那种行为在没有内联阶段的负载上就已经把它推得比
现在这条线还高。

顺带收紧了几条实测很稳、原来定得过松的:`inlineShowMs` 400 → 80,`inlineScrollP95Ms`
60 → 35,`inlineRowsMountedMax` 500 → 300,`inlineRowsTotalMin` 2000 → 2500。

`openSteadyP95Ms` 定在 80 而不是最初设想的 60:当时的估算是「稳态 p95 约 25」,四次实测
是 33.3–42.0,60 只剩 43% 余量,而这里每一条延迟线都留着 2–3 倍。判据本身(首次与稳态
分开)不变,变的只是那个数现在有四次运行撑着。

依据全部写在 `perf/thresholds.json` 的 `notes` 里,含每一条的实测区间 —— 换机器、换
Electron 版本或改夹具之后,重新推导需要的就是那些区间。

### 4. 顺带被抓到的一个丢数据的 bug

E2E 第一次运行就红了,而红的是**应用**。

`FileViewer` 用 `surfaceRef.current?.getText() ?? ''` 算 `dirty`。而 `内联` 和 `差异` 两个
视图**不挂载编辑器** —— AI 改过的文件恰恰默认以 `内联` 打开。于是没有编辑器可问,读到
`''`,拿它和非空文件一比,判定「有未保存修改」。

● 只是看得见的那一半。看不见的那一半是:草稿缓存**随即写入了一个空缓冲区**。再打开这个
标签,编辑器就以那个空草稿作为种子 —— 一次 Ctrl+S 就把用户的文件清空了。**每一个 AI 改过
的文件都在这条路上。**

修法是把「没有缓冲区」和「缓冲区是空的」分开:`isDirty` 的 `readText` 现在可以返回 `null`
(= 没有活的缓冲区,那么缓冲区**就是**磁盘快照),`FileViewer` 按「挂载的编辑器 → 草稿缓存
→ null」去读,`cacheNow` 在没有编辑器时**拒绝写**。`test/draftPolicy.test.ts` 钉住了三种
情况,E2E 里 `刚送达的改动文件不算「未保存」` 单独占一条 —— 它破坏的那个标题(「内容 ●」)
正是其它视图断言会去读的东西,混在一起会变成一句看不懂的「切到内容超时」。

**这正是八·2 里那句话的代价被兑现的地方:**「真正覆盖 CM6 集成的是性能门槛」——性能门槛
只问快慢,而这个 bug 跑得飞快。

## 十一、这三条也收掉了

- **`显示全文` 分支现在可达。**夹具多了第九个文件 `expandable.ts`(3,600 行、120 处改动),
  不算在八个标签的负载里,只被内联阶段单独打开 —— `FULL_VIEW_LIMIT` 是 4,000 行,那八个
  12,001 行的文件永远够不到这个分支。两条分支不是一回事:折叠时行数跟着**改动**走,展开时
  跟着**文件**走,后者才是当年会往文档里塞几千行的形状。实测:

  ```
  显示全文  1,079 → 3,721 行建模 · DOM 里最多 152 行(24.5×)· 展开 20.1 ms
  ```

  **两种分支下 DOM 里都是 152 行**,而建模行数差 3.4 倍 —— 窗口化跟着视口走,不跟着分支走,
  这正是要它证明的事。门槛判它自己那一对(`inlineFullRowsTotalMin` /
  `inlineFullRowsMountedMax`),E2E 判它的行为(省略行消失、建模行数变多、DOM 里的行数不到
  建模行数的一半)。`create()` 断言这个文件确实低于上限,否则按钮会被禁用、分支再次悄悄失守。
  加进第九个文件之后那一次运行,**每一条既有指标都落在此前五次已经量出的区间内** —— 它没有
  改变负载。
- **粗档那四条,答案是「两次运行,不是一次」。**`npm run perf:editor -- --gc-marks` 在每个
  阶段边界先强制回收再读堆,于是 `heapMarks` 量的是**活数据**而不是「V8 恰好要了多少页」。
  它必须是另一次运行:一次 major GC 要几十毫秒,而这些边界之间夹着计时按键和滚动的循环 ——
  把回收放进默认运行,就是拿延迟数字换内存数字。默认关闭;开启时报告打出一行提醒,说明那次
  运行的内存数字与默认运行**不可比**。
- **E2E 越过了编辑器。**Git 面板(列出真实 `git status`、暂存一个文件)和诊断中心
  (`/api/diagnostics/runtime` → SSE → 面板 → 点开跳到那一行)各自有了覆盖,夹具目录会
  `git init`、提交一次、再改一个文件。两项都收在**跨面板那条信号**上,所以它们仍然是关于
  编辑器的。git 不在 PATH 上时这两项**判失败而不是跳过** —— 没跑过的检查不算通过。

### 审查面板:没做,而且理由是不该做

`审查` 的状态只由一次**真实的 agent 回合**写入(`recordAgentTurn`,只在 OMP 聊天路径上被
调用),没有任何 HTTP 路由能记录一个回合。要覆盖它就得给产品开一条为测试而存在的路由。

**那正是这套 harness 从第一天起拒绝的东西。**Git 和诊断中心之所以进得来,恰恰因为它们的
状态有诚实的来源 —— 磁盘上的 git 仓库,和预览页本来就在用的上报端点;为它们没有改动产品
一行代码。要覆盖审查面板,该做的是让 harness 能驱动一次真的 agent 回合(一个说 RPC 协议的
桩 OMP),而不是开一个口子。那是一件独立的事,不是这件事的收尾。

## 十二、仍然开着的

- **粗档四条的分布**。六次运行足以说明它们很吵,不足以给出分布。`--gc-marks` 给了另一条更稳
  的量法,但它自己也才刚落地 —— 要用它来收紧默认那四条,得先攒够两种模式各自的样本,并确认
  两者之间的换算是稳的。
- **展开分支只有一次运行**。行数是确定性的(3,721 / 152),所以不变量那两条可信;`展开 20.1 ms`
  这一个数还不是区间。
- **`e2e` 里没有 Git 的写路径**(提交、回退、撤销修改)。暂存覆盖了「面板真的在读 git」,
  但提交会改变仓库状态,一次运行内的顺序得先想清楚;回退和 revert 更是如此。
- **桩 OMP**。它能一并解决审查面板的覆盖、诊断中心里 agent 来源的那半边,以及聊天流本身 ——
  现在这三处都靠 `harness/inject.js` 在渲染侧伪造上游,而那只到得了浏览器这一层。

## 十三、清理也会挂:E2E 第一次全绿那次没能退出

15/15 报完之后,进程停在那里,要手动 Ctrl+C。

```
UnhandledPromiseRejectionWarning: Error: EPERM, Permission denied:
  ...\botcf-e2e-editor
    at Object.rmSync → Object.remove (e2e/fixture.cjs) → cleanup (e2e/editor.cjs)
```

两个原因叠在一起:

1. E2E 的夹具目录是个 **git 仓库**,而 git 把 `.git/objects` 下的文件建成**只读**的,
   `rmSync(..., { force: true })` 对付不了它 —— `force` 只管「路径不存在」,不管权限。
2. 那个异常**逃出了 `cleanup()`**,于是后面的 `app.exit(code)` 根本没跑到。

第二条才是要紧的那条:**一个能挂死的收尾,和一个能挂死的测量工具是同一个毛病** —— 而这份
文档从第一节起就在说这件事。门槛里每一层 await 都有上限,偏偏清理这一段没有。

改动:`harness/tempDir.cjs` 把删除收成一个地方,内层用 Node 自己的 `maxRetries`
(它专门重试 EBUSY/EMFILE/ENFILE/ENOTEMPTY/**EPERM**),外层再留一圈循环给「Windows 在进程
退出后还会按住目录一会儿」这种情况,并且**永不 reject**;两个 runner 的 `cleanup()` 改成
先停服务再删夹具(服务是最可能还按着句柄的那个进程)、幂等、末尾 `.catch` 兜底。

**然后它又炸了一次,在另一头。**我修了拆的那一端,漏了搭的那一端 —— `create()` 开头还留着
同一句裸的 `rmSync`,而上一次被 Ctrl+C 掉的运行正好留下了一个删不掉的目录,于是新的运行
在生成夹具时就死了。同一个错误,隔着十行代码写了两遍。两处现在共用同一个删除器;删不掉时
`create()` 直接报错并告诉你手动删哪个目录,而不是拿一个「上次的改动已经提交过」的仓库继续跑
——那会让 Git 面板正确地显示「干净」,然后检查失败在一个跟面板毫无关系的理由上。

顺带一提:性能门槛的夹具没有 `.git`,所以它一直没被这个坑绊到 —— 同样的隐患它也有,只是
运气好。两边一起改了。

## 十四、第七次运行:为什么余量按离散度给,不按最大值给

修完清理之后那次门槛运行(第七次)在**代码没有任何变化**的情况下,一口气把四条指标的最大值
都推高了:

```
open steady P95   42.0 → 52.3 ms
renderer peak    280.8 → 300.3 MiB
inlineDelta      185.5 → 202.1 MiB
retainedDelta    100.5 → 106.1 MiB
```

**四条全部通过。**如果当初把线贴着「已观测最大值」去收(比如 open steady 定 60、renderer
peak 定 300),这一次就会红四条,并且被读成一次回退。

这也顺便结算了 §10.3 里那个偏离:`openSteadyP95Ms` 当时定 80 而不是最初设想的 60,理由是
「每一条延迟线都留着 2–3 倍」。第七次量到 52.3 —— **60 那条线会红。**

## 十五、上一次运行的残留:localStorage 决定了这一次看见什么

Git 面板那项在一次运行里 180 ms 通过,下一次超时了 —— 代码没动。

活动栏是**开关**(`dock.togglePart`:已经在最前面就关掉),而窗口的 origin 是固定的
`127.0.0.1:<port>`,于是 `localStorage` 跨运行存活,工作台把**停靠布局**和**打开的标签**
都存在那里。上一次运行结束时 Git 面板正好在最前面,这一次那一下点击于是把它**关掉**了,
检查就在等一个刚刚被自己关掉的面板。

编辑器那边的隐患更重:门槛的基线量的是**空工作台**,而它在打开任何文件之前采样 —— 一次
崩在半路、留下八个标签的运行,会让下一次的「空工作台」根本不空。它一直没被绊到,只是因为
每次运行最后都会 closeAll。

所以 `loadApp` 现在**加载 → 清空 localStorage/sessionStorage → 再加载一次**,两个 harness
共用。E2E 的 `openPart` 同时改成幂等的:传一个「这个面板一定会渲染的东西」进去,不在就点开,
在就什么都不做 —— 因为对一个开关来说,「点一下」和「打开」不是同一件事。

**一次运行不该取决于上一次是怎么结束的。**这条和 §13 是同一条:能被上次残留影响的测量,
和能挂死的测量一样,证明不了东西。
