# perf — 8 × 1 MB 编辑器负载门槛

`npm run perf:editor`

一次运行会:构建 → 生成夹具 → 启动本地服务(独立数据目录/端口) → 打开真实窗口 →
驱动真实组件 → 采样进程内存 → 按 `thresholds.json` 判定 → 写 `perf/last-run.json` →
清理。任一项超限时进程退出码为 1。

一次运行里有**两份负载**,分开记账:八个大文件当脏标签开着(P2-004 那份),以及同样八个
文件带上一份 AI 变更之后的 `内联` 差异视图。两者的内存不合成一个峰值 ——「八个大脏标签
要多少」和「三千行的差异视图要多少」是两句不同的话,合成一个数会让其中一个的回退藏在
另一个后面。

## 为什么存在

P2-004 的架构修复(只挂载活动查看器)在 2026-08-24 的核验里通过了,但性能症状本身
没有复测:没有数字,也没有阈值,于是"性能问题是否关闭"无法判定
(`docs/fix-verification-report-2026-08-24.md` 残余风险第 4 条)。这里把原报告的负载、
指标和判定线固定成可重复执行的一条命令。

## 负载

`fixture.cjs` 生成 8 个文件,每个 12,001 行 / 948,079 字节,全部作为**脏标签**打开。
两个数字都是有意的:12,001 行是让挂载的查看器变贵的原因(行数组 + 浏览器逐行排版的
textarea);刚好低于 1 MiB 是为了让每个标签**可编辑**——超过上限查看器只给只读预览,
而只读文件里量不出输入延迟。

另一半负载是每个文件 350 处 AI 改动的统一差异。这个数同样是按「必须能让它变贵」挑的:
`内联` 折叠视图为每处改动展开一个上下文窗口,再加每条被删的行和每段被省略的区间各一行,
350 处约合 3,150 行 —— 若全部渲染就是约 12,000 个元素,而视口加 overscan 只放得下约 160
行。这两个数之比正��门槛要判的东西。它同时被应用**从上面**卡住:每个文件的差异必须小于
`DIFF_CAP`,否则 `changedFiles` 只会留下尾巴,而被截断的夹具不是门槛以为自己写下的那个;
`buildSessionDiff` 会为此报错而不是交付。

夹具里还有**第九个文件** `expandable.ts`(3,600 行、120 处改动),它不算在八个标签的负载
里,只被内联阶段单独打开。理由是 `显示全文` 在超过 `FULL_VIEW_LIMIT`(4,000 行)时是禁用
的,而那八个文件都是 12,001 行 —— 于是展开分支在这里一直不可达,门槛测到的永远是折叠视图。
两条分支不是一回事:折叠时行数跟着**改动**走,展开时跟着**文件**走,后者才是当年会往文档
里塞几千行的那个形状。`create()` 会断言这个文件确实低于上限,否则按钮会被禁用、分支再次
悄悄失守。


## 指标

| 指标 | 含义 |
|---|---|
| `viewersWithEightTabs` | 8 个标签打开时页面上的查看器数量。修复的架构不变量:1,不是 8。 |
| `inputPaint` p50/p95/max | 按键到该帧**提交上屏**。门槛判的是这一个。 |
| `inputFrame` p50/p95/max | 按键到下一个 rAF 回调。同时报出来只是为了看它和 `inputPaint` 的差 —— 那个差就是 rAF 不等的布局和绘制。 |
| `inputBlock` | 按键事件同步返回的时间(React 对离散事件同步渲染),用于区分"渲染慢"和"排版慢"。 |
| `inputBreakdown` | `inputBlock` 拆成浏览器的部分和应用的部分;有哪几项取决于打字方式(见下)。 |
| `openFirst` / `openSteady` | 打开第一个标签 / 之后每个标签的耗时。分开报,理由见下。 |
| `tabSwitch` p95 | 点击标签到新文件内容可见。含重新读盘——只挂载活动查看器就要付这笔钱,所以它算在���面。 |
| `inline.rowsTotal` / `rowsMountedPeak` | 内联差异视图**建模**的行数,与它任何时刻**放进 DOM** 的最多行数。窗口化的不变量就是这一对。 |
| `inline.fullRowsTotal` / `fullRowsMountedPeak` | 同一对,但在 `显示全文` 展开之后、在那个 3,600 行的文件上。 |
| `inline.showMs` / `inline.scroll` / `inline.fullShowMs` | 切到内联到上屏;在其中翻页滚动、每页到上屏;以及点开 `显示全文` 到上屏。 |
| `rendererBaselineMiB` | **空工作台**(0 标签、已强制回收)的渲染进程工作集。所有内存判定都是相对它的增量。 |
| `loadDeltaMiB` | 编辑器阶段峰值 − 基线:8 个大型脏标签比空工作台多占多少。 |
| `inlineDeltaMiB` | 内联阶段峰值 − 基线:带 350 处改动的差异视图比空工作台多占多少。 |
| `retainedDeltaMiB` | 全部关闭并强制回收后 − 基线:两份负载合起来留下了多少没还。 |
| `jsHeapRetainedMiB` | 同上,但量 JS 堆。这是这里唯一能真正发现泄漏的数字。 |
| `heapMarks` | 每个阶段边界的 JS 堆(已用/已提交)。用来解释工作集峰值由什么构成:实测 JS 堆全程不超过 45 MiB 已提交,而工作集比空工作台高 400 MiB —— 差额是 Blink 为约 24,000 行保留的布局与字形结构,不是 JS 垃圾。 |

### 为什么「打开第一个标签」单独判

第一个标签除了读文件,还要拉取懒加载的编辑器 chunk;之后每一个都不用。八个样本的 p95
**就是**第���个,于是把它们合成一条线去判,等于把一次性成本读成每标签的回退 —— 这个混淆
差一点让代码分割被撤回(`docs/perf-gate-2026-08-28.md` §9 #4)。拆开之后每条线只说一件事,
任一条都能单独失败。

### 内联那一对为什么是��变量而不是耗时

`rowsMounted` 是视图放进 DOM 的行数,`rowsTotal` 是它建模的行数。只判前者会让一个**恰好
没产生几行**的夹具轻松通过,所以后者是一条**下限** —— 这里唯一的下限,它存在的意义就是让
不变量没法空手通过。

### 内联视图的差异是从哪来的

`内联` 只对「AI 改过的文件」存在,而门槛运行时没有 agent(更新器被指向死代理,正是为了
不在运行中途装一个)。`harness/inject.js` 因此**只伪造上游**:在一次发送期间替换 `fetch`,
且只替换 `/api/chat/stream`,回答一段真的 SSE 字节流;消息打进真实输入框、用真实回车发出。
从那段字节往后全是应用自己 —— `streamChat` 的解析、`changedFiles` 的合并、差异解析、按内容
重新锚定、行的构建。这和门槛早就在做的事是同一类:把不存在的上游,在它本该回答的地方
回答掉。生成器写出的 `+` 行**就是磁盘上的真行**,这不是细节:`anchorRegions` 会丢掉找不到
的块,一份对不上的差异会被应用悄悄化为乌有,而在空视图上量出来的数字非常好看。
`apps/web/test/sessionDiffFixture.test.ts` 用应用自己的解析器把这件事钉住。


### 为什么判 `inputPaint` 而不是 `inputFrame`

rAF 回调跑在它那一帧的样式、布局、绘制**之前**。原来的门槛判 `inputFrame`,于是任何
"把工作挪到回调之后"的改动都会显示成一次大幅胜利,而屏幕上什么都没变快。把强制同步
布局移出按键路径正是这样一种改动 —— 它确实是对的(浏览器随后能合并多次按键的布局),
但它的收益必须用上屏时间来结算,否则就是在给自己发奖状。`inputPaint` 从 rAF 回调里
再排一个任务,那是该帧提交之后第一个能跑的时刻。

### 打字方式

`document.execCommand('insertText')` 走 Blink 给真实按键用的同一条编辑命令,只改光标所在
那一行,并触发真正的 `input` 事件。

这个门槛原来的做法是每次按键把整个 948 KB 缓冲区通过原生 `value` setter 写回去。**那不是
按键。**整串替换会让 Blink 丢弃 textarea 的 inner editor 并重排全部 12,001 行,于是编辑器
被记账了真实打字根本不产生的工作;它还凭空造出一项 `写 value`(11.7 ms p50),而人打字时
插入由浏览器内部完成,缓冲区根本不经过 JS。它当时是这条门槛所报延迟的约 90%。

那个模式**已经删掉,而不是留在开关后面**:编辑面已经不是 textarea,复现不了;它产生过的
数字记在 `docs/perf-gate-2026-08-28.md` 里。

## 基线与阈值

`thresholds.json` 里的 `baseline` 是修复**之前**的实测值(每个标签都挂载查看器时):
短输入 714–904 ms、进程树峰值工作集 1,453.4 MiB、关闭 10 秒回落 0 MiB。`gate` 是本次
运行必须优于的判定线。除 `inlineRowsTotalMin` 一条是**下限**(见上,它是用来防止窗口化
不变量空手通过的)之外,其余每一条都是上限。**放宽任何一条,必须同时给出支持它的测量
结果。**

### 内存为什么改成量增量

原来的两条 —— `renderer after close ≤ 450 MiB` 和 `released after close ≥ 80 MiB` ——
都是照着"编辑器负载"写的,但采样从页面**已经加载完**才开始,所以它们实际判的是
「工作台 + 负载」。加一次基线采样、把判定改成相对���线的增量,是让门槛去判它自己写的那个
东西:`loadDelta` 问"标签花了多少",`retainedDelta` 问"关掉之后还剩多少"。

**这是把话说准,不是放宽。**第一次基线实测:空工作台 renderer 95.7 MiB,而失败那次运行
的峰值是 516.2 MiB、关闭 10 s 后 501.1 MiB —— 8 个标签确实加了约 420 MiB,也确实几乎
一点没还。旧的 `releasedAfterCloseMiB` 继续记录,只是不再作为判定。
详见 `docs/perf-gate-2026-08-28.md`。

另外,基线和关闭后的样本各自会先在页面里跑两遍 `window.gc()`(靠 `--expose-gc`),再读
`performance.memory.usedJSHeapSize`。空转十秒不是任何东西被释放的理由:V8 和
PartitionAlloc 不会主动把页还给操作系统,不强制回收的话,那个样本回答的是"没人施压时
分配器会不会还页",而这不是关于这个编辑器的问题。

这两件事**在页面里做,不走 CDP**。第一版用的是调试器:`Memory.forciblyPurgeJavaScriptMemory`
之后 detach,紧接着的 `executeJavaScript` 再也没有返回,整次运行在 30 秒上限处死掉,
什么都没量到。**能把被测对象弄死的工具不是测量工具。**在页面里做还有一个好处:按键附近
不存在任何附着的调试器,而延迟绝不能透过一个调试器去量。代价是没有 JS 堆"峰值"曲线,
但被判定的是"关掉标签之后还剩多少",那只需要两个离散样本。页面答不上来时
`jsHeapRetainedMiB` 为 null,该项**判失败而不是跳过** —— 没量到的门槛不算通过。

### 粗档那四条,和 `--gc-marks`

`rendererPeak` / `inlineDelta` / `jsHeapCommittedPeak` / `retainedDelta` 四条实测离散
23–140%,因为它们全都跟着**阶段结束时 V8 恰好向系统要了多少页**走 —— 同一个阶段在两次
运行里量到过 59.7 和 101.8 MiB 已提交。它们因此是「防止大幅回退」的粗线,不是精细的。

要精细地把分配归到某个阶段,用 `npm run perf:editor -- --gc-marks`:每个阶段边界先强制
回收两遍再读堆,于是 `heapMarks` 变成活数据而不是「V8 要了多少」。**它是另一次运行,不是
同一次的开关** —— 一次 major GC 要几十毫秒,而这些边界之间夹着计时按键和滚动的循环;把回收
放进默认运行就是拿延迟数字换内存数字。所以默认关闭,开启时报告会打出一行提醒:那次运行的
内存数字与默认运行**不可比**,别拿它当门槛结果用。

## 时限与失败输出

门槛自身有时限,这是修复而不是装饰。最初的版本里 `nextFrame()` 直接 `await`
`requestAnimationFrame`,main 进程对整段 `executeJavaScript` 也没有 watchdog;桌面会话
一旦停止投递帧回调,整条门槛就永久停在 `driving the editor…`——两次运行都没有产出
`last-run.json`,只能从外部终止。会挂死的测量工具证明不了任何性能结论。

现在每一层都有上限:

| 上限 | 默认值 | 覆盖方式 |
|---|---|---|
| 单次帧回调 | 5 s | `__PERF__.frameTimeoutMs` |
| DOM 等待(单条) | 60 s | `__PERF__.timeoutMs` |
| 渲染侧整段驱动 | 5 min | `__PERF__.totalMs` |
| 整次运行 | 8 min | `--budget <ms>` / `PERF_BUDGET_MS` |

驱动**不再抛异常穿过 `executeJavaScript`**,而是返回
`{ ok:false, stage, message, diagnostics, partial }`;main 进程把它连同最后一次阶段
上报写进 `last-run.json` 的 `failure` 区块。所以失败的运行同样有结构化结果:死在哪个
阶段、当时 `document.visibilityState` 是什么、已经测到的分位数是多少。总时限用尽时由
watchdog 走同一条路径,并照常清理窗口、服务、夹具和临时数据目录。

帧回调停摆最常见的原因是窗口被遮挡(Windows 上被其他窗口盖住即算 occluded,
`backgroundThrottling: false` 不覆盖这条路径),因此运行前会追加
`disable-backgrounding-occluded-windows` 等开关并把窗口置顶。

## 边界

- 只在 Windows/macOS/Linux 桌面会话里有意义:窗口必须可见且不被节流,否则帧回调的
  间隔就是节流间隔,量出来的是节流器不是编辑器。`--no-show` 仅用于排查,数字不可比。
- 只测渲染进程与 Electron 进程树。服务端进程不计入:P2-004 是渲染侧的问题,服务端的
  开销跟着请求走,不跟着标签数走。
- 运行期间不联网(更新器会被指向一个死代理),所以不会在测量中途下载 OMP 二进制。
- 会话是第三方模式,并且**会选好一条路由**——没有路由时对话输入框是禁用的,而内联阶段
  要从那里发出一次真实的发送。代价是路由存在时顶栏会每 15 s 拉一次模型健康;它对基线和
  负载**同样计入**,而且有路由才是用户真正待着的状态。
- 数据目录、端口、夹具都是临时的;用户自己的数据目录和工作区不会被动到。
- 引导代码(构建检查、服务、窗口、清理)在 `harness/app.cjs`,和 `e2e/` 共用;那边端口和
  数据目录都错开,两者可以同时跑。
